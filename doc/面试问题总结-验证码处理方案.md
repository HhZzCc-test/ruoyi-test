## 一、项目架构设计

### Q1: "介绍一下你的自动化测试项目架构"

> 项目采用四层分离架构：
>
> **第一层：API 客户端层**（`tests/core/client.py`）
> — 封装所有 HTTP 请求，统一管理 base URL、请求头、Session。所有接口调用集中在一个类中，便于维护。
>
> **第二层：测试工具层**（`tests/core/assertions.py` + `base.py`）
> — 提供四层断言策略（HTTP 状态码 → 业务码 → 字段存在性 → 数据类型），以及测试基类。
>
> **第三层：Fixture 依赖注入层**（`conftest.py`）
> — 使用 pytest 的 fixture 机制管理 Session 级别的 Token、API 客户端，各测试模块自动注入，避免重复登录。
>
> **第四层：测试用例层**（`tests/` 各模块目录）
> — 按业务模块拆分，每个模块有独立的测试文件和 conftest.py，互不干扰。

### Q2: "为什么选择 pytest 而不是 unittest？"

| 对比维度 | pytest | unittest |
|---------|--------|----------|
| 用例发现 | 自动发现 `test_*.py` | 需要手动维护 TestSuite |
| 参数化 | `@pytest.mark.parametrize` 原生支持 | 需要第三方库 ddt |
| Fixture | 依赖注入，支持 scope 控制 | setUp/tearDown 粒度粗 |
| 插件生态 | Allure、rerunfailures、xdist 等 | 较少 |
| 断言 | 原生 `assert`，失败信息清晰 | 需要 `self.assertXxx` 系列方法 |

> 我们项目用了 **Allure 报告**、**失败重跑**（rerunfailures）等插件，pytest 的插件生态是决定性优势。

### Q3: "项目中的 conftest.py 是怎么组织的？"

> 采用**层级化 conftest 机制**：
> - `tests/system/conftest.py`：系统管理模块专用，定义 `api_client`、`auth_headers`、`auth_token` 三个 Session 级 fixture
> - `tests/monitor/conftest.py`：系统监控模块专用，复用相同模式
> - 每个子模块的 conftest 通过 `autouse=True` 自动注入 `api_client` 到测试类
>
> **设计要点**：`scope="session"` 确保整个测试会话只登录一次，避免重复登录导致 Token 被挤掉。

## 二、验证码处理方案

### Q4: "你们自动化测试中怎么处理验证码？"

> 我们遇到了 RuoYi 框架的数学验证码问题。最初尝试了 OCR 方案，使用了 Tesseract 和 EasyOCR 两种引擎，但 RuoYi 的验证码带有干扰线和扭曲，OCR 识别率不足 30%，无法稳定运行。
>
> 后来分析验证码的生成机制，发现答案实际存储在 Redis 中，key 是 `captcha_codes:{uuid}`。我们直接通过测试代码连接 Redis 读取答案，实现了 100% 准确的验证码绕过。
>
> 这个方案相比 OCR 有三大优势：准确率 100%、零额外延迟、代码极简只需几行。

### Q5: "有没有尝试过 OCR？为什么失败了？"

> 尝试过两个方案：
> 1. **Tesseract OCR**：对图片做了灰度化→二值化→放大→去噪的预处理流水线，但 RuoYi 验证码的干扰线和扭曲导致识别结果如 `=7`、`4=?`、`4-457`，完全不可靠
> 2. **EasyOCR（深度学习）**：模型文件数百 MB，初始化极慢，对干扰严重的验证码仍无法稳定识别
>
> **教训**：OCR 不是万能药，分析后端存储机制往往更高效。

### Q6: "Redis 直读方案有什么坑？"

> 三个坑：
> 1. **Redis 协议不兼容**：新版 redis-py 默认用 RESP3，旧版 Redis 不支持 `HELLO` 命令 → 解决：`protocol=2`
> 2. **值带引号**：Redis 存储的值是 `"4"` 而非 `4` → 解决：`.strip('"')`
> 3. **Redis 不可用**：连接失败导致测试崩溃 → 解决：try/except + fallback 硬编码值

### Q7: "如果 Redis 也访问不了怎么办？"

> 我们做了三层降级：
> 1. 优先从 Redis 读取真实验证码
> 2. Redis 不可用时 fallback 到硬编码值（至少能让测试跑起来）
> 3. 同时在日志中告警，提示运维检查 Redis 连通性
>
> 长期方案：建议后端在测试环境提供"万能验证码"接口或配置开关。

## 三、认证与 Token 管理

### Q8: "测试中怎么管理 Token？"

> 核心设计：**Session 级别 fixture + 自动注入**
>
> ```python
> @pytest.fixture(scope="session")
> def auth_headers(api_client):
>     token = api_client.login_and_get_token("admin", "admin123")
>     api_client.set_auth_header(token)
>     return {"Authorization": f"Bearer {token}"}
> ```
>
> - `scope="session"`：整个测试会话只登录一次，避免 Token 被反复创建/销毁
> - `autouse=True` 的 fixture 将 `api_client` 自动注入每个测试类
> - 各测试模块通过 `conftest.py` 共享，无需重复编写登录逻辑

### Q9: "Token 过期了怎么办？"

> 当前项目使用短期 Token，但因为 `scope="session"` 且测试通常在 1-2 分钟内完成，暂未遇到过期问题。
>
> 如果要做长时间测试，有两种方案：
> 1. **主动刷新**：在 fixture 中监控 Token 过期时间，过期前自动调用 refresh 接口
> 2. **懒加载**：每次请求前检查 Token 有效性，无效则重新登录（适合并发场景）

### Q10: "怎么测试未认证和无效 Token 的场景？"

> 需要绕过 Session 的默认认证头。我们使用 `requests.get()` 直接发请求，而不是 `self.client.session.get()`：
>
> ```python
> # 未认证测试 - 使用 requests 直接请求，不携带 session 的认证头
> resp = requests.get(
>     self.client._url("/monitor/online/list"),
>     headers={"Content-Type": "application/json"}
> )
> assert resp.json().get("code") == 401
> ```
>
> 关键点：不能用 `self.client.session.get()`，因为 session 已被 fixture 设置了 Authorization 头。

## 四、测试用例设计方法论

### Q11: "你的测试用例设计流程是什么？"

> 我们遵循**四阶段强制流程**（写在 SKILL.md 中作为团队规范）：
>
> ```
> 阶段一：接口分析 → 阶段二：用例文档 → 阶段三：代码编写 → 阶段四：验证执行
> ```
>
> **核心原则：文档先行，禁止跳过用例文档直接写代码。**
>
> 具体来说：
> 1. 先分析所有接口的路径、参数、响应模型、认证要求
> 2. 写出详细的用例规格文档（TC-XXX-NNN），每个接口至少覆盖 1 正常 + 2 异常 + 1 边界
> 3. 严格按照用例文档编写测试代码，不允许漏写或多写
> 4. 运行验证，发现断言不匹配后端行为时，回到文档更新后再改代码

### Q12: "怎么保证测试覆盖率？"

> 通过**场景覆盖矩阵**来量化管理：
>
> | 接口 | 用例ID | 正常 | 异常 | 边界 | 权限 | 总计 |
> |------|--------|:----:|:----:|:----:|:----:|:----:|
> | 在线用户列表 | TC-ONLINE-001~004 | 1 | 1 | 1 | 1 | 4 |
> | 定时任务列表 | TC-JOB-001~004 | 1 | 1 | 1 | 1 | 4 |
>
> 每个接口至少覆盖 4 个维度：正常功能、异常输入、边界值、权限控制。

### Q13: "用例文档和代码怎么保持同步？"

> 通过**用例ID锚定**机制：
> - 每个测试方法第一行标注 `"""TC-XXX-NNN: 用例标题"""`
> - 用例文档中的 TC-XXX-NNN 与测试代码一一对应
> - 修改代码前必须先找到对应的用例文档
> - 发生不一致时，优先更新文档，再修改代码（文档是唯一真相来源）

## 五、pytest 高级特性

### Q14: "pytest fixture 的 scope 有哪些？你项目中怎么用的？"

| scope | 生命周期 | 项目中的使用 |
|-------|---------|-------------|
| `function` | 每个测试函数 | 测试类内的 `_setup` fixture |
| `class` | 每个测试类 | 未使用 |
| `module` | 每个模块 | 未使用 |
| `session` | 整个测试会话 | `api_client`、`auth_headers`、`auth_token` |

> Session 级别的 Token 管理是整个项目的基础设计决策，确保整个测试套件只登录一次。

### Q15: "参数化测试怎么用的？"

> 以登录测试为例：
>
> ```python
> login_success_data = [
>     ("admin", "admin123"),
>     pytest.param("admin", "admin123", id="boundary_username_min"),
> ]
>
> @pytest.mark.parametrize("username,password", login_success_data)
> def test_login_success(self, username, password):
>     code, uuid = self.get_captcha_code_and_uuid()
>     resp = self.client.login(username, password, code, uuid)
>     self.assert_business_success(resp.json())
> ```
>
> 使用 `pytest.param` 的 `id` 参数给每组测试数据命名，失败时能快速定位是哪组数据出问题。

### Q16: "pytest.mark 怎么用的？"

> 我们定义了两级标记：
> - `@pytest.mark.smoke`：冒烟测试，核心功能
> - `@pytest.mark.critical`：关键功能，仅次于 smoke
>
> 运行方式：
> ```bash
> pytest tests/ -m smoke        # 仅跑冒烟
> pytest tests/ -m "not smoke"  # 跳过冒烟
> ```

## 六、断言策略与错误处理

### Q17: "你们的断言策略是什么？"

> **四层断言策略**（从外到内逐层验证）：
>
> 1. **HTTP 状态码**：`assert resp.status_code == 200`
> 2. **业务码**：`assert data.get("code") == 200`（正常场景）或 `== 401`（未认证）
> 3. **字段存在性**：`assert "rows" in data` / `assert "data" in data`
> 4. **数据类型**：`assert isinstance(data.get("rows"), list)`
>
> 封装在 `tests/core/assertions.py` 中：
> - `assert_http_ok(resp)` — 第 1 层
> - `assert_business_success(data)` — 第 2 层
> - `assert_business_error(data)` — 异常场景的业务码断言
> - `assert_field_exists(data, field)` — 第 3 层
> - `assert_field_not_empty(data, field)` — 第 3+4 层

### Q18: "测试失败了怎么排查？"

> 我们的排查流程：
> 1. 看 pytest 输出中的 `AssertionError` 行，定位具体断言
> 2. 看 Allure 报告中的请求/响应详情（附在测试步骤中）
> 3. 确认是代码问题还是后端行为变更：
>    - 代码问题 → 修复代码
>    - 后端行为变更 → 回到用例文档，更新预期，再改代码
> 4. 修复后重新跑该模块，确保回归

## 七、测试报告与 CI/CD

### Q19: "怎么生成测试报告？"

> 使用 Allure 框架：
> ```bash
> pytest tests/ --alluredir=allure-results
> allure serve allure-results
> ```
>
> 代码中通过装饰器标注：
> - `@allure.feature("模块名")` — 一级分组
> - `@allure.story("子功能")` — 二级分组
> - `@allure.title("具体标题")` — 用例标题
> - `@allure.severity(allure.severity_level.CRITICAL)` — 严重级别
> - `with allure.step("步骤描述"):` — 测试步骤

### Q20: "怎么集成到 CI/CD？"

> 推荐方案：
> 1. Jenkins/GitLab CI 中配置定时触发或代码提交触发
> 2. 执行 `pytest tests/ --alluredir=allure-results --junitxml=report.xml`
> 3. 使用 Allure Jenkins Plugin 生成趋势报告
> 4. 失败时发送通知（邮件/钉钉/企业微信）
> 5. 设置失败重跑：`pytest --reruns 2 --reruns-delay 5`

## 八、Redis 相关技术

### Q21: "项目中 Redis 用来做什么？"

> 两个用途：
> 1. **验证码答案存储**（后端行为）：RuoYi 将数学验证码答案存在 Redis，key 为 `captcha_codes:{uuid}`
> 2. **测试代码读取**（我们的方案）：测试代码直连 Redis 读取答案，绕过 OCR 识别

### Q22: "Redis 连接配置怎么做？"

> ```python
> self._redis = redis.Redis(
>     host="localhost",
>     port=6379,
>     protocol=2,          # 兼容旧版 Redis
>     decode_responses=True # 自动解码为字符串
> )
> ```
>
> 三个关键参数：
> - `protocol=2`：新版 redis-py 默认 RESP3，旧版 Redis 不支持 HELLO 命令
> - `decode_responses=True`：避免手动 decode
> - 连接参数可通过配置文件管理，方便不同环境切换

## 九、实际问题与解决方案

### Q23: "遇到过哪些印象深刻的 Bug？"

| 问题 | 根因 | 解决 |
|------|------|------|
| 登录全部失败 | 验证码硬编码为 `"1234"` | Redis 直读真实验证码 |
| 系统管理 401 | 测试未携带 Token | 通过 conftest 注入 Session 级 auth fixture |
| 用户状态筛选断言失败 | 后端筛选不精确，status=0 筛出了 status=1 | 改为断言"结果中包含 status=0"，而非"全部为 status=0" |
| 不存在资源返回 200 而非 500 | RuoYi 后端对不存在的 ID 返回空数据+code=200 | 断言改为匹配实际行为 |
| `_get()` 不支持 params | 方法签名遗漏了 `params` 参数 | 添加 `params=None` 并透传 |
| monitor 模块 fixture 未找到 | conftest 中引用 fixture 但未定义 | 在 monitor 的 conftest 中完整定义 fixture |

### Q24: "怎么处理测试环境依赖问题？"

> 1. **Redis 不可用** → try/except + fallback
> 2. **注册功能未开启** → 检测 `msg` 中"没有开启注册功能"，`pytest.skip()`
> 3. **缓存名称为空** → 先获取列表，为空则 `pytest.skip()`
> 4. **后端服务未启动** → fixture 初始化时捕获连接异常，给出明确提示
>
> 核心原则：**不要让环境问题导致测试崩溃，优雅降级或跳过。**

### Q25: "测试数据怎么管理？"

> - **用户名生成**：`generate_unique_username()` 使用 UUID 保证唯一性
> - **参数化数据**：使用 `pytest.mark.parametrize` 在测试函数级别定义，数据和逻辑不混杂
> - **固定数据**（如 admin/admin123）：定义在测试文件顶部的常量列表中
> - **不依赖数据库**：所有测试数据通过 API 接口创建和验证，不直接操作数据库
